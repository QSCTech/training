# 产品推广、反馈与增长

产品发布后，需要让目标用户知道它、愿意尝试它，并把使用中的问题带回下一轮迭代。本节点整理自原资料中的“产品推广”“用户反馈的收集”和“数据与增长”。先完成[需求分析、调研与验证](product-research-validation.md)，再结合实际项目实践。

## 制定推广计划

先写清目标人群、他们在哪里接触信息、希望完成的动作，以及如何衡量效果。线下宣传品、电子屏、公众号推文或视频适合的场景不同，选择渠道时应考虑覆盖人数、制作与审批成本、发布时间和用户的实际使用习惯。

一份最小推广策划可包含：项目背景、目标用户、核心信息、渠道与时间、负责人、预算、预期效果和应急预案。文案先讲用户能解决的问题，再说明具体使用方式。不要只用曝光量评价效果，还要看访问、激活和后续留存。

## 收集并整理反馈

主动收集可用访谈、定向问卷或页面内提示；被动收集可用反馈入口、邮件、群聊或 Issue。主动提问应尽量选对用户和时机，避免打扰；被动渠道应明显、易用，并说明预计处理方式。

收到反馈后，保留用户原话，同时按产品、版本、用户群、场景和问题类型编码。常见类型包括使用疑问、Bug、改进建议、新功能建议和正负面评价。编码帮助团队找出重复问题，但不能替代阅读原始描述。

| 类型 | 首要动作 | 交给谁 |
| --- | --- | --- |
| 使用疑问 | 解释流程，检查引导是否清楚 | 运营与产品 |
| 可复现 Bug | 收集环境、版本、步骤、预期和实际结果 | 测试与研发 |
| 需求或改进建议 | 追问使用场景、频率和替代办法 | 产品 |
| 情绪反馈 | 尊重回应，寻找可进一步确认的事实 | 运营 |

不要要求用户在公开渠道提供密码、令牌或不必要的个人信息。转交 Bug 时，优先写清复现步骤和必要条件，而不是只说“无法登录”。处理后告知用户结果，并把高频问题沉淀到 FAQ。

## 用数据指导迭代

围绕“看到推广 → 开始使用 → 完成核心任务 → 再次使用”设定少量指标。对不同渠道和用户群分别观察，避免只看总量。对每项改进记录假设、基线、发布时间、观察窗口和结果；同时结合访谈判断指标变化的原因。

## 练习

- [ ] 为自己的项目写一页推广策划，说明目标人群、渠道、时间、负责人和衡量指标。
- [ ] 把至少五条模拟反馈分类，选出一条 Bug 写成可复现的 Issue。
- [ ] 设计一个从反馈到修复、回复用户、更新 FAQ 的处理流程。
